# Deployment

## Current setup

- Host: **GitHub Pages**
- Source: branch `main`, folder `/` (repository root)
- URL: <https://somphol.github.io/khan-trig-unit4-equations-identities-studio/>
- Build step: none. Pages serves the files as committed.
- `.nojekyll` is present so Jekyll never rewrites or ignores files.

The deployment is intentionally the simplest supported path: no Actions artifact,
no environment variables, no secrets.

## Deploying a change

```bash
git add .
git commit -m "feat: …"
git push origin main
```

Pages rebuilds on the push. A typical rebuild is under a minute.

## Verifying a deployment

```bash
BASE=https://somphol.github.io/khan-trig-unit4-equations-identities-studio

curl -s -o /dev/null -w "%{http_code}\n" "$BASE/"          # 200
curl -s "$BASE/" | grep -o "<title>[^<]*</title>"
curl -s -o /dev/null -w "%{http_code}\n" "$BASE/style.css"
curl -s -o /dev/null -w "%{http_code}\n" "$BASE/script.js"
curl -s -o /dev/null -w "%{http_code}\n" "$BASE/state.json"
```

Then open the page, switch all three tabs, and check the console.

## Cache behaviour

GitHub Pages sends short-lived caches. After a push, a stale `style.css` or
`script.js` can survive for a few minutes in a browser or CDN edge. Hard-reload
or append a query string when verifying. The app itself has no service worker,
so there is no offline cache to invalidate.

## Custom domain

1. Add the domain in **Settings → Pages → Custom domain**.
2. Create the DNS records GitHub shows (apex `A`/`AAAA` or `CNAME` for `www`).
3. Enable **Enforce HTTPS** once the certificate is issued.
4. Add a `CNAME` file only if you manage the domain manually; the Pages UI can
   create it for you.

No application code depends on the host, so a move to Netlify, Cloudflare Pages
or S3 only requires uploading the repository root.

## Rollback

Because every deploy is a commit, roll back by reverting the offending commit:

```bash
git revert <sha>
git push origin main
```

or redeploy a previous commit through the Pages UI. Do not rewrite `main` for a
teaching site; a revert keeps history honest.

## Release tags and Pages

Tags do not trigger a separate Pages deployment in this setup. The live site
always reflects `main`. Publish a GitHub Release for the tag (see
[RELEASE.md](RELEASE.md)) so the source snapshot and the live site correlate.

## CI

`.github/workflows/ci.yml` runs static checks only. It does not deploy and has
no write permissions. Pages deployment remains branch-based, so a red CI run
does not block a manual push — check the Actions tab before releasing.

## State record

`state.json` describes the original 1.0.0 build (time, tokens, credits). It is
not generated by deployment and should not be rewritten to look newer.
